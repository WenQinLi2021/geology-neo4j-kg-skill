# Geology Neo4j KG Skill 技术交付文档

## 1. 文档信息

- 文档名称：`Geology Neo4j KG Skill 技术交付文档`
- 适用对象：知识图谱项目经理、数据整理人员、Codex 使用者、地质专业复核人员
- 交付对象：`geology-neo4j-kg` Codex skill 及其配套脚本、模板、说明文档
- 当前版本：`v1.0`

## 2. 交付目标

本交付物用于将地质科研报告知识图谱的生产流程标准化、模板化和可复用化，使团队成员能够基于统一规则完成以下工作：

1. 读取地质科研报告
2. 抽取实体、关系、属性与证据链
3. 对多批次抽取结果进行融合与规范化
4. 管理不确定知识与复核事项
5. 生成 Neo4j 可执行导入文件

本 skill 的设计目标不是替代地质专业判断，而是将“抽取、整理、导出”这一重复性流程固化为标准作业能力。

## 3. 适用范围

当前版本优先适用于以下类型项目：

- 稀土、三稀、稀散元素相关知识图谱
- 成矿规律与找矿方向类报告
- 地层、岩性、矿床类型、元素富集、风化剖面类知识抽取
- 以 Neo4j Desktop 或 Neo4j Aura 为目标图数据库的项目

对于其他矿种或其他学科方向，可在保留本流程框架的前提下扩展 schema。

## 5. 总体方法论

本 skill 固化的不是“整份 PDF 一键入图”的黑箱模式，而是一套证据链驱动的人机协作流程：

```text
源报告
-> 分批抽取 JSON
-> 融合与规范化
-> review_flags 管理
-> Neo4j 导出
```

该流程的核心原则如下：

- 先定本体，再做抽取
- 先输出中间 JSON，再做图数据库导入
- 每条关系尽量保留句级证据
- 不确定知识不混入高置信度导出
- 多报告之间必须经过规范化再导出

## 6. 角色分工建议

### 6.1 业务/项目负责人

负责：

- 明确项目目标与范围
- 决定本批次报告主题边界
- 决定导出策略是否仅保留高置信度事实

### 6.2 Codex + Skill 执行方

负责：

- 读取报告
- 依据 schema 抽取知识
- 进行规范化、融合、去重、标记 review_flags
- 生成可导入 Neo4j 的 Cypher

### 6.3 地质专业复核人员

负责：

- 复核 review_flags 项
- 复核争议实体、关系方向和规范化决策
- 决定延后导入知识是否进入正式图谱

## 7. 标准处理流程

### 7.1 阶段一：本体与规则锁定

在正式抽取前，应先明确以下内容：

- 图谱目标类型
  - 资料检索型
  - 推理分析型
  - 报告辅助型
- 本体最小集
- 命名规范
- 证据链字段
- 抽取粒度
- 导出范围与质量门槛

建议默认使用“小而稳”的 v1 方案，优先保证可追溯、可校验、可迭代。

### 7.2 阶段二：分批抽取

建议按 `1-3` 份同主题报告为一批处理，不建议过度分散主题。

每批次抽取时：

- 以页段、章节或事实密集片段为单位处理
- 输出标准 extraction JSON
- 将测量值、含量、厚度等写入结构化属性
- 保留原文写法与规范名

### 7.3 阶段三：融合与规范化

在该阶段需要完成：

- 别名归并
- 简称与全称统一
- 同名实体消歧
- 重复关系去重
- 冲突事实标记
- review_flags 归集

此阶段的目标不是“消灭所有差异”，而是“让差异被显式记录和管理”。

### 7.4 阶段四：Neo4j 导出

推荐默认导出策略：

- 实体置信度 `>= 0.90`
- 关系置信度 `>= 0.90`
- 排除被 `review_flags` 命中的项
- 仅导出低争议、事实型关系
- 剪除未与导出关系相连的孤立实体

## 8. review_flags 管理机制

`review_flags` 是本 skill 的质量控制核心机制之一。

其用途是将以下内容从首轮生产导出中隔离出来：

- 低置信度实体
- 低置信度关系
- 规范化歧义
- 报告间冲突
- 明显偏研究推断而非已验证事实的表达

推荐处理策略：

1. 首轮只导出高置信度事实
2. 将 `review_flags` 项留待专业人员复核
3. 复核后再单独生成补充导入批次

## 10. 标准调用方式

### 10.1 推荐通用调用模板

```text
Use $geology-neo4j-kg.
继续处理这批地质科研报告，按当前 schema 抽取、融合、保留 review_flags，并导出 Neo4j Desktop 可直接导入的 Cypher。
```

### 10.2 面向阶段的调用模板

#### A. 本体设计

```text
Use $geology-neo4j-kg.
请先设计这个项目的最小本体，目标是在两周内落地 Neo4j v1。
输出实体类、关系类、唯一键、证据字段和抽取粒度。
```

#### B. 正式抽取

```text
Use $geology-neo4j-kg.
按当前 schema，从这批报告中抽取实体、关系、属性和证据链。
输出 JSON，不要解释。
```

#### C. 融合与规范化

```text
Use $geology-neo4j-kg.
把这些 extraction JSON 融合到现有 normalized graph。
统一规范名，合并别名，保留冲突项到 review_flags。
```

#### D. Neo4j 导出

```text
Use $geology-neo4j-kg.
基于 merged normalized JSON，导出高置信度、低争议的 Neo4j Cypher，并输出导出摘要。
```

## 11. 推荐项目目录结构

建议项目统一使用如下结构：

```text
project/
  schema/
  sources/
  extractions/
  normalization/
  neo4j_export/
```

说明如下：

- `schema/`
  存放本体、字段约束、JSON schema
- `sources/`
  存放原始报告
- `extractions/`
  存放按批次输出的 extraction JSON
- `normalization/`
  存放融合、规范化、去重后的主图谱文件
- `neo4j_export/`
  存放 Cypher、CSV、导出摘要、导入辅助文件

## 12. Neo4j 导出脚本说明

导出脚本路径：

[`skills/geology-neo4j-kg/scripts/build_neo4j_cypher.py`](../skills/geology-neo4j-kg/scripts/build_neo4j_cypher.py)

脚本支持：

- 按实体置信度阈值过滤
- 按关系置信度阈值过滤
- 限定允许导出的谓词集合
- 排除 `review_flags`
- 生成 Neo4j 中文显示字段更新脚本
- 输出 summary JSON

示例命令：

```powershell
python ".\skills\geology-neo4j-kg\scripts\build_neo4j_cypher.py" `
  --input-json "C:\path\to\roundX_merged_normalized.json" `
  --output-cypher "C:\path\to\roundX_high_confidence.cypher" `
  --summary-out "C:\path\to\roundX_high_confidence_summary.json" `
  --display-zh-out "C:\path\to\roundX_display_zh.cypher" `
  --entity-confidence-min 0.9 `
  --relation-confidence-min 0.9 `
  --safe-predicates "belongsToUnit,locatedIn,hasDepositType,hostedIn,occursInProfile,partOfProfile,overlies,underlies,locatedOnInterface,formedByWeatheringOf,formedDuring,enrichedIn,containsMineral,occursAs,adsorbedBy,leachedFrom,carriesElement,hasAnomaly"
```

## 13. 质量控制与验收建议

建议从三个层面做验收：

### 13.1 抽取正确性

- 抽样检查实体类型是否合理
- 抽样检查关系方向是否正确
- 抽样检查证据句是否支撑该三元组

### 13.2 规范化正确性

- 检查同名异写是否被错误拆分
- 检查简称和全称是否被错误合并
- 检查跨报告实体是否被重复建点

### 13.3 导入正确性

- Neo4j 中节点数和关系数是否符合预期
- 是否出现大量重复关系
- 是否将 review_flags 项错误导入生产图谱

## 14. 当前限制

当前版本存在以下限制：

- 不替代地质专业判断
- 不自动解决复杂理论冲突
- 不适合将所有低置信度知识直接入库
- 当前 schema 主要围绕 rare-earth / three-rare 项目抽象而来

如团队需要支持更多矿种，应在保持主流程稳定的前提下扩展 schema，而不是直接强行复用现有类目。

## 15. 维护建议

当以下内容发生变化时，应同步更新 skill：

- 本体结构
- 关系命名规则
- review_flags 策略
- Neo4j 导出策略
- 团队标准提示词模板

建议每次更新后至少验证：

- skill 是否仍可被 Codex 正确识别
- 导出脚本是否仍能生成合法 Cypher
- 示例批次是否仍能复现预期节点数与关系数

## 16. 结论

`geology-neo4j-kg` skill 已将地质知识图谱项目中最容易重复、最容易漂移、最容易出错的部分沉淀为标准流程。

对于团队而言，它的核心价值不是“替代思考”，而是：

- 统一工作方法
- 降低协作成本
- 保持图谱结构一致
- 提高增量构建效率
- 为后续专业复核保留证据基础

建议将本 skill 作为团队知识图谱生产的标准入口，并以实际报告批次持续迭代。
